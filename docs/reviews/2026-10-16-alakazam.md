## Answers to the four questions

**1. Does the kit's taxonomy support §6's claim?** Partly, and the sentence should not stand as written. The kit does count
operational retrieval as RAG (`build-rag-systems/SKILL.md:10`), but its definition is retrieval of *prior decisions,
mappings, classifications and reviewer corrections* to drive a *runtime decision* with scoring, thresholds and review
(taxonomy:29-48). The CRM agent has none of that: no decision corpus, no thresholds, no review loop (item 4). What it
is, in the kit's own words, is grounded generation ("knowledge Q&A or grounded generation", `agents/alakazam.md:13`)
whose retrieval is "hybrid search over operational data" (`agents/alakazam.md:18`): the first four steps of the kit's
retrieval pipeline (normalize, filter, deterministic match through `resolve_search_center`, lexical candidates) feeding
a model that only reports returned rows. The kit's retrieval pipeline also has a vector step (retrieval policy:21) and
its non-negotiables require OpenSearch for production vector or hybrid retrieval (SKILL.md:173); the design omits that
step. Item 1 gives the accurate wording; items 2 and 3 record the omission as a README override (in the CRM) and as a
deviation with a path to close it (in the pipeline).

**2. Which "must include" items apply, which are justified deviations?**
- *Bedrock embeddings* and *OpenSearch vector or hybrid search*: **README override** in this repository (item 2). An
  index over county data is ingestion and a second copy of Travis data; README.md:25 and :40 put that in the pipeline
  story. The requirements move to the pipeline, where the lexical leg already exists (DuckDB full-text) and the vector
  leg does not (item 3 and the contract proposal below).
- *SAM local emulation*: **applies** (item 5). It is cheap, kit-prescribed, and the CRM's plan is silent on it while
  §3's "SAM as IaC" exclusion could be misread as excluding the emulator. CDK stays the only IaC.
- *Docker OpenSearch replay*: **not applicable** (item 6): there is nothing to seed. Its purpose, replaying golden
  fixtures against the retrieval layer and comparing ids and decisions rather than prose, is kept through the
  `PipelineClient` fixture adapter and the golden set (item 7).

**3. Does the design meet the README's "RAG-backed agent"?** As written in the README, yes: README.md:24 asks for an
agent that answers natural-language questions "using available property and permit data", README.md:13's own example
is a spatial and numeric filter, and the design answers it from retrieved, cited rows with explicit misses. Two things
make the absence of any semantic leg the largest conformance risk in §6 all the same: the kit's RAG pipeline expects a
vector or hybrid step, and the kit's evaluator, deriving its probes from the story, decomposes the sibling
property-intelligence story into "semantic RAG Q&A" (`evaluate-candidate-intent/SKILL.md:71`) and probes "RAG-backed
retrieval over the real records" (`assignment-evidence-catalogs.md:36`); lexical search misses paraphrases ("storm
damage" vs "hail", "tear-off" vs "re-roof", "membrane" vs "TPO"). The CRM must not build the leg (item 2); the pipeline
API has to serve it, as an additive `v1` change before the field-level freeze (`api-contract.md:274-279,293`). The
contract change is below; the CRM's side is item 3.

**4. MCP tools or wrapped REST; is a separate CRM agent justified?** Wrap REST through the typed client (item 22):
no kit rule mandates MCP as the agent transport, the kit's explicit-registration rule rules out MCP tool discovery, and
a second transport for the same eight operations would be a parallel path with no new capability. Keep the tool names
and schemas identical to the MCP table so the choice stays a transport detail. A separate CRM agent is justified (item
23): the README puts the agent in the CRM, the agent needs CRM-owned write tools the read-only pipeline must never
hold, the pipeline chat route is throttled at 1 request/s, and an agent calling an agent doubles cost and latency and
turns structured rows into prose before the CRM sees them, which the kit's retrieval policy warns against
(retrieval policy:94).

## Proposed contract change (for the pipeline repository's `docs/api-contract.md`, additive to v1)

The contract rule is "additive only (new optional params, new nullable fields)" (`api-contract.md:3-4`) and "If the CRM
needs something new, change this file in this repository first, then the server, then the CRM" (:293). Everything
below is optional or nullable, so old clients are unaffected. The CRM's decisions.md records only the request and the
agent's behaviour (item 3); the pipeline records the acceptance, the storage choice and the dated contract change.

### A. `GET /v1/permits/text-search` gains `mode`

- New optional param `mode`: `lexical` (default; exactly today's behaviour) or `hybrid`. No vector-only mode: the kit
  forbids embeddings alone where lexical and deterministic signals exist (`build-rag-systems/SKILL.md:170`).
- `hybrid`: the current full-text candidates (top 100 by rank) and the vector candidates (top 100 by cosine similarity
  of the embedded `q` against the permit corpus in C) are fused by reciprocal rank fusion (k = 60), then the existing
  filters apply unchanged (`lat`/`lon`/`radius_miles`, `status_group`, `roofing_only`), then `limit`/`cursor` page the
  result. Candidate counts and the fusion constant are server constants, not params; `score` is the fused score.
- New nullable response fields, present on every text-search response:
  - top level `retrieval`: `{mode_requested, mode_applied, fallback_reason: null | "vector_index_unavailable" |
    "embeddings_unavailable", lexical: {index: "duckdb_fts", version}, vector: null | {store, embedding_model,
    embedding_version, dimension, corpus_scope, indexed_count, built_at, run_id}, fusion: null | "rrf"}`.
  - per item, beside the existing `score` and `match_snippet`: `score_components: null | {lexical_rank, vector_rank,
    lexical_score, vector_similarity}` and `matched_on: null | string[]` (the fields the lexical leg matched).
- Fallback: `mode=hybrid` with no vector index or with embeddings unavailable returns `200`, `mode_applied: "lexical"`
  and a `fallback_reason`; a missing leg is never a `5xx`. This is what lets the CRM agent always ask for `hybrid`.
- MCP: `search_permit_text` gains the same optional `mode` and returns the same `retrieval` block.

### B. `GET /v1/meta` and the Run record gain `retrieval`

`retrieval: {text_index: {index: "duckdb_fts", version, indexed_permits}, vector_index: null | {store,
embedding_model, embedding_version, dimension, corpus_scope, indexed_count, built_at}}`. The CRM footer and the agent's
`get_run_summary` read it; the Run record carries the same object so each run states how its indexes were built and
with which embedding version (the kit forbids silent re-embedding with another model,
`implementation-local-poc-to-opensearch-migration.md:56`).

### C. The corpus (pipeline side, in the kit's corpus-contract vocabulary)

One record per building permit in the full-text index's scope (trade permits excluded); if the deploy-time cost gate
rejects the full set, the scope narrows to `is_roofing` or `needs_review` permits and `corpus_scope` says so. `id` =
`permit_id`; `source_hash` = `record_cid` where present, else the sha256 of the embedded text; `text_for_embedding` =
`description | work_class | permit_class | permit_type` as printed, nothing synthesized; filter metadata =
`status_group`, `roof_work_class`, `is_roofing`, `lat`, `lon`, `geo_id`, `property_id`, `run_id`,
`work_classifier_version`; `embedding_model`, `embedding_dimension`, `embedding_version` on every record. Embeddings are
computed at deploy with Bedrock (the kit's current suggestion for Bedrock is `cohere.embed-v4:0`, with
`amazon.titan-embed-text-v2:0` acceptable, `build-local-rag-pocs/SKILL.md:94-98`; verify availability in `us-east-2` on
the account first, since Bedrock enablement is pending there), written to S3 beside the DuckDB file with deterministic
ids so a rebuild is idempotent, behind a cost gate that prints token count and price before the full embed. A model
change creates a new `embedding_version` and is compared on the golden queries in E before reads switch.

### D. Where the vectors are served (the pipeline's decision; stated here so the contract stays storage-agnostic)

The kit's rule is OpenSearch Service or Serverless (`architecture-aws-local-emulation.md:45`) and no relational-vector
store (:50). Either OpenSearch option carries a standing monthly cost, which conflicts with the pipeline README's
"Design the infrastructure so Oracle does not carry ongoing infrastructure cost by default" and "Use DuckDB for local or
portable analytical querying"; that README overrides the kit for the pipeline, exactly as the CRM's README does here.
The zero-standing-cost alternative is vectors inside the deploy-time DuckDB file (a fixed-size `FLOAT[n]` column with
`array_cosine_similarity`; brute force over a roofing-scoped corpus of tens of thousands of rows runs well under a
second in the Lambda, and the `vss` HNSW extension only if measured necessary). That is a relational-vector store, so
the pipeline must record it as a README override of `architecture-aws-local-emulation.md:50`. `retrieval.vector.store`
names whichever was chosen.

### E. Golden queries that decide whether the leg is worth switching on

Pairs where the lexical leg misses and hybrid should hit: "storm damage re-roof" against descriptions that say "hail";
"tear off and replace shingles" against "re-roof"; "flat roof membrane replacement" against "TPO"; "roof leak repair"
against "patch". The pipeline measures recall@10 lift on these against the live corpus; the CRM switches its default
request from `lexical` to `hybrid` only after that comparison (the kit's compare-before-switching-reads rule), and
reports `mode_applied` in `limitations` either way.

### F. Lower priority: `GET /v1/contractors/search` (item 24)

Params `q` (required, at least 3 characters), `lat`, `lon`, `radius_miles` (optional, together), `limit`, `cursor`.
Matching over `company_name` and `printed_names[]`: normalized exact, then prefix, then trigram similarity at or above
0.4, in that order; no embeddings (short labels). Response `{items: [{contractor_attribution_key, identity_status,
company_name, printed_names, permit_count, open_permit_count, roofing_permit_count, bbb, match_method: "exact" |
"prefix" | "similar", similarity}], total, next_cursor}`; MCP tool `search_contractors`.
